# git-commit lessons

- 2026-10-27: Your final message IS the report: write it out in full (plan ids or hashes, title, full message, files, Black result, co-author, left out). One run committed correctly but returned only "placeholder", so the caller had to reconstruct everything from git.
- 2026-10-27: Building a partial `--content` file: write it as bytes (`open(f, "wb")` / `sys.stdout.buffer.write`) with LF line endings. Text-mode output on Windows adds CRLF, which makes the planned blob differ from HEAD on every line. Prefer building the content from HEAD's version plus your lines over filtering `git diff` hunks.
- 2026-10-27: To split `tests/snapshots/*.json` by build, load HEAD's JSON, copy in only the wanted build keys from the working file, write `json.dumps(d, indent=1, sort_keys=True) + "\n"` as LF bytes (reproduces HEAD exactly) to a scratchpad file, and plan it with `--content <path>=<file>`.
- 2026-10-27: For a partial `.claude/skills/agent-index/SKILL.md` (or any line-based file): start from `git show HEAD:<path>`, copy only the wanted rows from the working file by prefix (e.g. "| [`name`]"), fix the counts in headings, write LF bytes, plan with `--content`. Don't hard-code row text: other agents may change the working file mid-run.
- 2026-10-27: To check that a commit passes tests on its own, export it (`git archive <hash> | tar -x -C <scratchpad dir>`) and its parent the same way, run `./run_tests.sh -q` in both, and diff the sorted `FAILED` lines: only new failures count. 4 tests in test_format_changed.py/test_skill_scripts.py always fail in such an export (CRLF in the .sh files). This caught spell data that would have broken 20 tests on main; on 2026-10-28 HEAD itself had 24 export failures.
- 2026-10-28: Run `git log --oneline A..B` as its own command (or after an `echo ---` marker), not chained after `git log -N`: its output blended into the plain log and was misread as empty.
- 2026-10-28: A path can be in only one pending plan, so one file's hunks can't go to two commits in one plan run: combine those groups, or plan one part with `--content` and leave the rest (`--left`) for a plan made after apply (Notes/discovered-issues.md with a user's line and Claude's entries). On 2026-10-30 a 5-feature brief with 4 files shared by features 2-4 needed plan runs after each apply; build every stage now (HEAD plus asserted exact-string inserts, assert the last stage == working tree), test each stage in an export, and hand the later stages' content and messages to the caller.
- 2026-10-30: Re-planning one plan to fix its message makes it newer than plans recorded after it (apply goes oldest first): drop and re-record the later ones too. Write scratch Python with the Write tool, not a bash heredoc: a heredoc holding `'''` strings failed with "unexpected EOF".
- 2026-10-28: Two git-commit runs can get the same brief at once: another run planned the feat files 2 s before my `new`, which then refused them as "already in pending plan". Re-run `list` just before each `new`; if another plan already covers the brief's files and `check` says ready, don't drop or duplicate it: report its id and message as part of your report.
- 2026-10-28: Check every number or source you put in a message against the commit that made the content (`git show -s <hash>`), not an agent's memory note: "the 34 Arcana Unleashed spells" was really 30 from Arcana Unleashed plus 4 from a D&D Beyond drop.
- 2026-10-28: push-check to a branch whose remote lags main lists every commit already on origin/main as "not yours" and refuses. Report it with `git log origin/main..<hash>` (only yours) vs `origin/<branch>..<hash>` so the user sees that a main push, or a branch push after they confirm the backlog, would be clean.
- 2026-10-29: A planned path that shows `MM` in `git status` (an older version staged in the shared index) makes `check`/`apply` block the plan ("other staged changes in the index"). Run `check --all` right after planning, add a `--note`, and tell the caller the index must match the working tree (they `git add` it) before apply; apply the plans together so a data/docs plan doesn't land before the code it needs.
- 2026-10-29: Plans stack on the HEAD they were made at; if that base is itself unpushed (7a524cc6 here), push-check refuses even a "push without confirmation" brief. In plan mode, run `git log --oneline origin/<target>..HEAD` and flag any unpushed base commit in the report so the user can OK it before apply.
- 2026-10-29: When your own MEMORY.md is in a pending plan, don't edit it in the same run (the plan blocks as changed since planning); put the lesson in the report and add it after apply/push.
